Here’s what I traced through the minting pipeline:

When a board is minted the game jumps into func_C4B94F (code/bank_04.asm:16480). That routine streams text into SRAM by walking through the script referenced by TextPointerTable.
Any byte ≥ $F0 is treated as a control code. The $FF terminator that closes each leaderboard entry hits the handler at func_C4BA53. Aeon Genesis patched that handler: note the jsl.l func_FE01DE block at code/bank_04.asm:16644.
func_FE01DE lives in text.asm:2544. It takes the current text ID, subtracts $6007 (see func_FE01FF), and converts the result into an offset/DBR for the LeaderboardNames array. In other words, the handler no longer reads the raw Text1312…1333 blocks; it copies from LeaderboardNames instead.
The issue is that LeaderboardNames (see text.asm:2433) is still ASCII-based padding—each entry is 16 single-byte codes with @ filler. When func_C4BA88 pulls those bytes, it only masks off the low 8 bits before writing to SRAM, so the values that end up in memory are the ASCII indices, not the 16‑bit tile IDs the renderer expects. With the font Tables the engine is using at mint time, the lower-byte pattern $20, $21, $22, … all map to the small kana family, which is why you’re seeing the repeated “ぃ”.
So the current flow is: text ID → func_FE01DE → LeaderboardNames ASCII codes → $FF control terminator. No part of this path uses the Text1312 data we’ve been editing; the SRAM writer expects each name to already be encoded as 16‑bit tile values.
The practical consequence is that we have two ways forward:

Keep the existing redirection (func_FE01DE) and replace each entry in LeaderboardNames with 16 tile words (or 16 bytes where each byte is the low glyph ID and the high byte already includes the $38xx tile base). That mirrors how the original Japanese ROM stored its defaults.
Bypass LeaderboardNames entirely by undoing the func_FE01DE hook and making Text1312…1333 point at proper tile data. Then func_C4B94F can work like it did originally.
Either route ends with the same requirement: the minting handler must see data that’s already in the game’s glyph format (a byte where the low 6 bits index the font and the high bits select the tile page), not simple ASCII indices. In the Japanese ROM those words looked like $38xx values; once we rebuild the English set to use that scheme the minting pipeline will copy correct defaults into SRAM.

When we rewired LeaderboardNames to hold 64 tile-coded entries in ROM, we didn’t touch that staging buffer. Result: Wall Scroll Cave still reads whatever the old patch preloaded (the Japanese default), copies it into SRAM, and the renderer shows it verbatim.
